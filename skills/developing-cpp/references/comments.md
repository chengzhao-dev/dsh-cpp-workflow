# 注释

注释分四层：文件头、类型注释、函数注释、实现注释；配置文件的注释另算。层级越靠外，越讲概念与契约；越靠里，越讲实现理由。同一件事只写一次。

## 总则

- **第一句先写结果、限制或检查项**：类型用名词短语写它是什么；普通函数写正常返回什么、失败时返回什么或抛什么；布尔查询与 `operator==` 写「检查…是否…」，不写「返回 true/false」。条件、参数与实现理由放第二句以后。
- 公共注释回答「这是什么」和「调用方必须遵守什么」；实现注释回答「为什么这样写」和「边界在哪里」。设计取舍、方案对比与演进历史写到书稿、README 或提交说明。
- 用中文散文写完整句子，句号结尾；标识符、标准库类型、`@param` 这类标签保持原文。
- 行宽跟项目 `.clang-format` 的 `ColumnLimit` 走（Google 基线是 80 列，中文按两列计）；横幅与列宽同宽，不另设数字。
- 写之前三问：删掉这句，读者会误解设计或做错事吗？这句只是复述签名或代码吗？这个限制能不能由类型、`const` 或 `[[nodiscard]]` 表达？第一问为否就删，第二问为是就删，第三问为是就改代码。
- 命名、分文件、`enum class`、异常与结果类型这类全项目风格约定只写进项目文档与读者正文；注释不替项目解释风格。

## `///` 与 `//` 的分工

- `///` 只给声明：头文件里的类型、函数、枚举值与公开数据成员（行尾补一句用 `///<`）。调用方和 Doxygen 从这里取契约。
- `//` 给实现：函数体内的步骤与边界说明、局部变量、文件头横幅、配置文件的说明。
- 不给局部变量和函数体里的语句写 `///`；文件头也不写成 `///`，否则编辑器会把它挂到紧随其后的第一个声明上。
- 判断看一句话写的是「调用方要遵守的承诺」还是「维护者要知道的写法」：前者用 `///`，后者用 `//`。

## 长度预算

| 层 | 行数 | 第一句 | 写什么 |
| --- | --- | --- | --- |
| 文件头 | 3–6 | 这个文件是什么 | 由哪几部分组成、不负责什么 |
| 类型注释 | 2–14 | 名词短语：这个类型或取值是什么 | 只有类的不变量 |
| 函数注释 | 3–10 | 正常返回什么、失败时返回或抛什么、检查什么 | 参数与失败方式 |
| 数据成员 | 行尾 1 句，名字与类型已自明时不写 | 名字和类型看不出的范围、初值含义 | 什么时候变 |
| 实现注释 | 1–3 | 为什么这样写或边界在哪里 | 代价 |


## 文件头

每个手写源文件开头写一段文件头：这个文件负责什么、分成哪几块、不负责什么。不写作者、版权年份、变更日志和外部资料路径。

```cpp
//===----------------------------------------------------------------------===//
// board.h - 定义井字棋棋盘。
//
// 棋盘只保存格子状态与规则判断，不含对局流程；对局流程在 game.h。
//===----------------------------------------------------------------------===//
```

- C++ 用 `//`，CMake 用 `#`，YAML/JSON 用 `#` 或 `//`。
- 横幅宽度等于 `ColumnLimit`：`//===` 起头、`===//` 收尾，中间补 `-`；章节横幅同一格式。
- 超过约 200 行的文件用章节横幅分组，组名是读者要跳转的锚点；一个文件不超过 8 个横幅。

## 类型注释

对象是类、结构体、枚举和类型别名。第一句是名词短语：类写「这个类型是什么」，纯数据结构和枚举写「这个取值表示什么」。

只有类有不变量，而且不重复领域尺寸时，才加第二段「限制」。纯数据结构和枚举不写第二句。


```cpp
/// 井字棋棋盘。
class Board {
```


禁止事项：

- 不写成员清单，不按声明顺序复述接口。函数各自的契约写在函数上。
- 不写跨类分工。边界靠类型与所有权表达，注释只写本类型保证什么。
- 不写类型系统已经表达的性质（`值语义`、`所有查询都是 const`）。
- 不写尚未发生的用法、方案对比与取舍论证、广告句。
- 纯数据结构不写「只保存…，不拥有…，不含…」这类否定式边界；这些由成员类型和所有权表达。
- 领域尺寸不写进类型注释：格子数由 `cells_` 的声明表达，棋盘边长由 `kBoardRows`、`kBoardCols` 表达。
- 枚举与只承载数据的结构体：第一句是名词短语，写这个取值表示什么；需要条件时用 `///<` 补一句可核实的条件。

## 函数注释

两段式，短函数可以只留第一段：

1. 结果、限制或检查项：普通函数写返回什么、失败时返回或抛什么；布尔查询与 `operator==` 写「检查…是否…」。
2. 契约：`@param`、`@return`、`@throws`，写范围、单位、所有权和失败方式。


```cpp
/// 放置成功返回 true；坐标越界、目标已占或要写空格子时返回 false，不抛异常。
///
/// @param position 目标行列坐标。
/// @param cell_type 要放置的棋盘格子类型，必须是 kX 或 kO。
[[nodiscard]] bool PlaceCell(CellPosition position, CellType cell_type);
```

- 布尔查询与 `operator==`：第一句写「检查…是否…」；`@return` 只写「什么情况下为 true」，再补一句「不检查什么」。
- `@param` 要么全写，要么全不写；写范围、单位或所有权，不写「索引」这类同义反复。
- `@return` 在返回类型自明时可以省略；`[[nodiscard]]` 已表达「必须使用」时不再重复。
- `@throws` 必须与 `references/exceptions.md` 一致；不抛异常的函数不写。
- 私有函数同样写契约，不能默认调用者知道前置条件；输出参数标 `[out]`，既读又写标 `[in,out]`。

## 数据成员与实现注释

数据成员在名字和类型已经说清时不写行尾注释。只保留需要说明单位、哨兵值、外部约定或所有权的成员：写「单位或哨兵 + 外部约定 + 什么时候改写」，同类成员对齐。`cells_`、`count` 这类不复述存储布局；`current_player_` 与 `result_` 这类需要读者知道取值含义或改写时机的保留。

```cpp
Player current_player_ = Player::kCross;  // 开局 X 先手；每次落子后切换。
GameResult result_ = GameResult::kInProgress;  // 终局后不再改写。
```

实现注释只写读者看不出、但下一次修改会踩到的三样东西：为什么这样写（而不是另一种写法）、这里的边界条件、这样做的代价。1–3 行，放在被解释语句上方；第一句先写理由或边界，不复述代码，也不写变更史。

`.cpp` / `.cc` 的函数体默认**不写**注释：公开契约已经在头文件的 `///` 里，实现再写一遍只会随代码漂移。大型工程的共识是把接口说明留在声明上——[Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html#Implementation_Comments) 只在难懂、不明显的地方写实现注释，并明确不要描述代码本身；[LLVM Coding Standards](https://www.llvm.org/docs/CodingStandards.html#commenting) 同样要求写意图而不是逐步翻译。文件头横幅保留，它对应两家的文件说明，不是函数体解说。

唯一保留的一类：删掉这句话，下一次修改会得到错误结果，而且代码本身看不出那个结果。句子要写出错误结果，不写「省掉一次扫线」这类口号。典型位置：

- 次序依赖：先判胜再判满，否则最后一子会变成平局。
- 类型收窄与解析：先按 64 位读再收窄；解析失败后必须丢掉整行。
- 状态不变量、外部格式、回退路径、刻意重复。
- 共享方式：`thread_local` 之类的可见性。

循环体里逐行复述 `push_back`、`return` 的注释一律删；不写变更史、外部资料路径和注释掉的代码。CMake 的契约注释不在这里，写法见 `../../configuring-cmake/references/cmake.md`。

## TODO、配置、改写次序与边界

`TODO:` 后先写定位（阶段名或 issue 号），再写一个短横线，再写动作；不写 `TODO(某人)`，不写没有动作的 TODO。

`.clang-format`、`.clang-tidy`、`.clangd`、CMake 的配置项旁边写「为什么这样设」，不写「这一项是什么」；配置注释贴在被解释的键上方。

只改注释时仍走第 3、4 步，然后回读：文件头 → 类型（名词短语 + 只有类的不变量）→ 函数（结果/失败方式/检查项 + 参数）→ 数据成员（名字类型看不出的含义）→ 实现（为什么/边界）→ 术语与新符号是否真实存在 → 运行 `checking-comments.mjs` 兜底。

- 注释写给维护者，正文写给读者；设计理由、方案比较与算法取舍写在正文或实现注释里，公开接口只留契约。
- `///`、`@param`、横幅不进入 `.qmd`、YAML、CSS。
- 禁止：用注释代替类型/`const`/`[[nodiscard]]`；大段表格、装饰图案、表情；外部资料路径、跨仓库引用、团队流程；成员功能清单；注释元叙述（「其余内容见某处」「两处不重复」）。
