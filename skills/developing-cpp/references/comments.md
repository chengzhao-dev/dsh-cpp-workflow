# 注释

注释分四层：文件头、类型注释、函数注释、实现注释；配置文件的注释另算。层级越靠外，越讲概念与契约；越靠里，越讲实现理由。同一件事只写一次：外层写过，内层就不再重复。

## 总则

- 注释回答「这是什么」和「调用方必须遵守什么」，不回答「为什么这样设计」。设计取舍、方案对比与演进历史写到书稿、README 或提交说明。
- 用中文散文写完整句子，句号结尾；标识符、标准库类型、`@param` 这类标签保持原文。
- 篇幅由内容决定：一句话说得清就写一行，有使用约定就把约定写完整。不为了短砍掉契约，也不为了长凑行数。
- 行宽跟项目 `.clang-format` 的 `ColumnLimit` 走（Google 基线是 80 列，中文按两列计），超了就换行；横幅与列宽同宽，不另设一套数字。
- 写之前做三问：删掉这句，读者会误解设计或做错事吗？这句只是复述签名或代码吗？这个限制能不能由类型、`const` 或 `[[nodiscard]]` 表达？第一问为否就删，第二问为是就删，第三问为是就改代码，不写注释。
- 命名、分文件、`enum class`、异常与结果类型这类全项目风格约定只写进项目文档与读者正文；注释不替项目解释风格，也不写「用 X 而不是 Y」的理由。

## `///` 与 `//` 的分工

- `///` 只给声明：头文件里的类型、函数、枚举值与公开数据成员（行尾补一句用 `///<`）。调用方和 Doxygen 从这里取契约。
- `//` 给实现：函数体内的步骤与边界说明、局部变量、文件头横幅、配置文件的说明。写给人读，不进文档索引。
- 不给局部变量和函数体里的语句写 `///`；文件头也不写成 `///`，否则编辑器会把它挂到紧随其后的第一个声明上。
- 判断只看一句话写的是「调用方要遵守的承诺」还是「维护者要知道的写法」：前者用 `///`，后者用 `//`。主流指南一致：Doxygen 只为文档化的声明生成条目，Google 与 LLVM 都在声明上用 `///`、在函数体内用 `//`。

## 长度预算

| 层 | 行数 | 写什么 |
| --- | --- | --- |
| 文件头 | 3–6 | 这个文件是什么、由哪几部分组成、不负责什么 |
| 类型注释 | 6–14 | 概念、使用约定 |
| 函数注释 | 3–10 | 承诺、参数与失败方式 |
| 数据成员 | 行尾 1 句 | 存什么、范围或单位、初值的含义 |
| 实现注释 | 1–3 | 为什么这样写、边界、代价 |

行数只是防止失控的锚点，不是配额。内容不够就少写，像「检查棋盘是否已满」这种名字已经说清的，一句契约即可。

## 文件头

每个手写源文件开头写一段文件头：这个文件负责什么、分成哪几块、不负责什么。不要写作者、版权年份、变更日志和外部资料路径。

```cpp
//===----------------------------------------------------------------------===//
// board.h - 定义井字棋棋盘。
//
// 棋盘只保存格子状态与规则判断，不含对局流程；对局流程在 game.h。
//===----------------------------------------------------------------------===//
```

- C++ 用 `//`，CMake 用 `#`，YAML/JSON 用 `#` 或 `//`。
- 横幅宽度等于 `ColumnLimit`：`//===` 起头、`===//` 收尾，中间补 `-`。章节横幅同一格式，宽度取当前 `ColumnLimit`（Google 基线 80）。
- 超过约 200 行的文件用章节横幅分组，组名是读者要跳转的锚点；一个文件不超过 8 个横幅。列宽随项目改，横幅跟着改一次，全文一致。
- 生成文件、第三方文件、纯数据文件不写文件头。

## 类型注释

对象是类、结构体、枚举和类型别名。写两段，段间空一行：

1. 概念：它在领域里表示什么，读者能对上棋规、词义或界面。
2. 约定：本类型自己保证什么、调用方必须遵守什么（不变量、取值范围、失败方式、所有权与生命周期）。

不写设计段落：为什么这样切分职责、为什么不选另一种写法，属于书稿的设计讨论，注释里不出现。分层说明放文件头，类注释只讲本类型。

```cpp
/// 井字棋棋盘。
///
/// 3×3 个格子，每格取空、X 或 O；格子数量不会改变，落子只改变单个格子的取值。
class Board {
```

判据：删掉这句，读者会不会做错事、或把它用到别的类型上？读签名、`const`、`[[nodiscard]]` 或成员类型就知道的事，写出来只是重复一遍，删。

按下面的次序取内容，够了就停，不必每段都凑满：

1. 一句话职责：这个类型是什么、给谁用。
2. 使用约定：什么时候该用它、失败与前置条件是什么。
3. 非显然保证：所有权、生命周期、异常保证、复杂度；签名里看得出的不写。
4. 线程规则：只有实例会被多个线程访问时才写，写清哪些操作可以并发、哪些要调用方自己同步。
5. 不变式：几条始终成立的条件；能写成 `assert` 或 `static_assert` 的，写断言而不是注释。

禁止事项：

- 不写成员清单。`提供检查坐标区间、检查棋盘格子是否为空、……的功能` 这类句子会把接口抄一遍，接口一改就过期，而且没告诉读者怎么用。函数各自的契约写在函数上。
- 不按声明顺序复述一遍接口，不复制函数注释。
- 不写跨类分工。`谁该落子、落子被拒后怎么提示留在 Game` 说的是另一个类型，读者既没法验证，重构一次就过期；边界靠类型与所有权表达，注释只写本类型保证什么。
- 不写类型系统已经表达的性质。`值语义，可以自由拷贝`、`所有查询都是 const` 由类声明与 `const` 直接给出，不写。类型系统表达不了的保证才值得写：深拷贝不共享可变状态、只读并发安全、异常安全等级，而且要能被测试或断言验证。
- 不写尚未发生的用法。`对局和搜索可以交替读取同一棋盘` 描述的是以后可能出现的调用方；注释只写当前契约，新用法落地时再补它必须遵守的约定。
- 不写方案对比与取舍论证：`用 X 而不是 Y`、`比……更……`、`复制的代价可以忽略`、`只留一份实现` 这类句子属于设计讨论，不进注释。
- 不写「本类使用快速排序所以很快」这种广告句；要写清楚代价与适用规模。

枚举与只承载数据的结构体可以短一些：概念一段，`///<` 先写这个取值表示什么，需要时用冒号补一小句读者能核实的补充（条件、动作或结果）；两段都要短，不重复名字，不写「因为……所以……」的长句。

```cpp
/// 对局结果。
enum class GameResult : std::uint8_t {
  kInProgress = 0,  ///< 游戏进行中：还可以落子。
  kCrossWin = 1,    ///< X 获胜：达成三连。
  kNoughtWin = 2,   ///< O 获胜：达成三连。
  kDraw = 3,        ///< 平局：棋盘已满，双方都没有三连。
};
```

冒号后的补充只要是读者扫一眼就能核实的条件就够了；要展开判定过程或推导，留给函数实现注释或正文。

## 函数注释

两段式，短函数可以只留第一段：

1. 承诺：这个函数给调用方什么结果，一句话，不复述函数名。
2. 契约：`@param`、`@return`、`@throws`，写范围、单位、所有权和失败方式。

```cpp
/// 在指定坐标放置棋子。
///
/// 越界、已占或要写空格子都返回 false，不抛异常。
///
/// @param position 目标行列坐标。
/// @param cell_type 要放置的棋盘格子类型，必须是 kX 或 kO。
/// @return 放置成功返回 true；坐标越界、要写的是空格子或目标已有棋子时返回 false，棋盘不变。
[[nodiscard]] bool PlaceCell(CellPosition position, CellType cell_type);
```

- 布尔查询：`@return` 写「什么情况下为 true」，再补一句「不检查什么」。例如 `IsCellEmpty` 不判断对局是否结束，这句话必须写，否则调用方会替它想。
- `@param` 要么全写，要么全不写；参数名已经能说明意思的，与其写「索引」，不如写取值范围或所有权。
- `@return` 在返回类型自明时可以省略；`[[nodiscard]]` 已表达「必须使用」时不再重复。
- `@throws` 必须与 `references/exceptions.md` 的声明一致；不抛异常的函数不写。
- 私有函数同样写契约：调用者可能是同一个类的另一个成员，不能默认它知道前置条件。
- 参数是输出参数时标 `[out]`，既读又写时标 `[in,out]`。

## 数据成员与实现注释

数据成员用行尾注释，写「存什么 + 范围或单位 + 初值的含义」，同类成员对齐。

```cpp
Board board_;                             // 对局棋盘。
Player current_player_ = Player::kCross;  // 当前轮到的玩家，开局时 X 先手。
```

实现注释只写三样东西：为什么这样写、这里的边界条件、这样做的代价。1–3 行，放在被解释语句的上方。

```cpp
// 只有对手能立刻成线时才挡：先看自己的胜手，避免把能赢的一步让给对方。
if (CanWinNow(game, player)) {
  return win_move;
}
```

- 不逐行翻译代码，不在 `if` 与 `else` 之间挂注释，分支理由写进各自分支内部。
- 允许写局部取舍（为什么这里接受 O(n²)、为什么排序要稳定、为什么缓存这一层）；不写变更史（「原来……现在……」）和外部资料路径。
- 注释掉的代码不保留，需要的从版本历史取。

下面这些位置**每处都要有一条实现注释**，它们决定读者能不能看懂逻辑，不是可选的润色：

- 次序依赖：几项更新必须按某个次序做，或两种判断的先后会改变结果（先判胜再判满、先验坐标再写数组）。
- 类型收窄：从宽类型读入再检查能否收进窄类型，或 `static_cast` 之前的范围判断。
- 输入与解析：为什么清失败位、为什么丢弃整行、为什么按 64 位读再收窄。
- 外部格式：手写 JSON、协议字段顺序、编码处理的约定，以及改动时要同步的文件。
- 回退路径：`switch` 覆盖全部枚举后仍留的 `return`、断言拦不住的兜底分支、`continue` 而不是报错的场合。
- 状态不变量：写入后哪些成员已经一致、失败时为什么不需要撤销。
- 刻意重复或刻意不共享：为了可读性重复一小段判断、为了零依赖不复用库函数。

有这些位置时不受 1–3 行预算约束：先写清为什么，再检查能否删。反过来，循环体里逐行复述 `push_back`、`return` 的注释一律删。

## TODO

```cpp
// TODO: 阶段 3 - 支持撤销任务状态更新
// TODO: issue #42 - 把编号检查抽到 TaskTable
```

`TODO:` 后先写定位（阶段名或 issue 号），再写一个短横线，再写动作。不写 `TODO(某人)`，不写没有动作的 TODO。

## 配置注释

`.clang-format`、`.clang-tidy`、`.clangd`、CMake 的配置项旁边写「为什么这样设」，不写「这一项是什么」。

```yaml
# 列宽、缩进、包含顺序都取 Google 预设，不逐项覆盖。
Language: Cpp
BasedOnStyle: Google
Standard: Latest
```

- 配置注释贴在被解释的键上方，不写策略头和文档路径。
- `.clang-format` 按逻辑组分段，每组一句说明这一组在管什么，不逐键写「设置 X 为 Y」。
- `.clangd` 每个键组一句话，说明为什么需要这个数据库或参数。
- `.clang-tidy` 的每个关闭项写一句理由；没有理由的关闭项删掉。同一个理由只写一次。

## 语言与术语

- 注释用中文；标识符、标准库类型、命令、错误消息保持原文。
- 同一个概念只用一种译法，术语表见 `references/glossary.md`；中文与英文、数字之间留一个空格。
- 不写「显然」「众所周知」这类评判读者的词，也不写「注意」「重要」这类没有信息量的加重。

## 改写次序

只改注释时仍走第 3、4 步，然后按这个次序回读：

1. 文件头：是什么、由哪几块组成、不负责什么。
2. 类型注释：概念、约定；删掉成员清单与设计论证。
3. 函数注释：承诺、参数与失败方式；与 `references/exceptions.md` 一致。
4. 数据成员：存什么、约束、初值。
5. 实现注释：只留为什么和边界，逐行字幕全部删掉。
6. 回读：同一概念一种译法；注释里出现的新函数名、新常量是否真的存在。
7. 机械化兜底：`node "<skill-dir>/scripts/checking-comments.mjs" --root <项目根>` 检查横幅宽度、禁止标签、注释与声明的贴合、类型成员清单、设计论证、`@param` 完整性与枚举行尾注释；它不判断内容好坏，只守住格式底线。

## 与读者正文的边界

- 注释写给维护者，正文写给读者；两边各自写自己的文件，不互相抄。
- 设计理由、方案比较与算法取舍写在正文或实现注释里，公开接口注释只留契约。
- `///`、`@param`、横幅不进入 `.qmd`、YAML、CSS。

## 禁止

- 用注释代替类型、`const`、`[[nodiscard]]` 能表达的限制。
- 大段 ASCII 表格、装饰图案、表情符号，以及把注释当提交说明或变更日志。
- 写外部资料路径、跨仓库引用、团队流程；这些属于文档。
- 写成员功能清单（`提供……、……的功能`）与按声明顺序复述接口。
- 写注释的元叙述：不交代「其余内容见某处注释」「两处不重复」「成员用法写在行尾注释里」这类注释布局；读者要的事实直接写出来，不写「哪里写了什么」。
