# 注释

注释按写作、布局、排版、润色四节组织；文件头、类型、函数与实现注释是注释所在的位置，配置文件的注释另算。位置越靠外，越讲概念与契约；越靠里，越讲实现理由。同一件事只写一次。

按四类改动查：写作决定写什么，布局决定放哪一层哪一行，排版决定符号、宽度与标签，润色删复述、统一句式。四步都可能删句子，但后置条件和成员约定只有写作能定，润色不得以「精简」为由删掉。

## 写作：只写声明里看不出的事实

- **第一句先写结果、限制或检查项**：类型用名词短语写它是什么；普通函数写正常返回什么、失败时返回什么或抛什么；布尔查询与 `operator==` 写「检查…是否…」，不写「返回 true/false」。条件、参数与实现理由放第二句以后。
- 公共注释回答「这是什么」和「调用方必须遵守什么」；实现注释回答「为什么这样写」和「边界在哪里」。设计取舍、方案对比与演进历史写到书稿、README 或提交说明。
- 用中文散文写完整句子，句号结尾；标识符、标准库类型、`@param` 这类标签保持原文。
- 写之前三问：删掉这句，读者会误解设计或做错事吗？这句只是复述签名或代码吗？这个限制能不能由类型、`const` 或 `[[nodiscard]]` 表达？第一问为否就删，第二问为是就删，第三问为是就改代码。
- 命名、分文件、`enum class`、异常与结果类型这类全项目风格约定只写进项目文档与读者正文；注释不替项目解释风格。
- 状态结论必须带成立条件。「终局后空格仍在」没有说清哪种终局；写成「一方已三连而棋盘尚未占满时，空格仍然留着；平局时棋盘已满，没有空格」。删掉前提换来的短，不算润色。

### 类型：名词短语与不变量

对象是类、结构体、枚举和类型别名。第一句是名词短语：类写「这个类型是什么」，纯数据结构和枚举写「这个取值表示什么」。

只有类有不变量，而且不重复领域尺寸时，才加第二段「限制」。纯数据结构和枚举不写第二句。

```cpp
/// 井字棋棋盘。
class Board {
```

禁止事项：

- 不写成员清单，不按声明顺序复述接口。函数各自的契约写在函数上。
- 不写跨类分工。边界靠类型与所有权表达，注释只写本类型保证什么。
- 不写类型系统已经表达的性质（`值语义`、`所有查询都是 const`）。
- 不写尚未发生的用法、方案对比与取舍论证、广告句。
- 纯数据结构不写「只保存…，不拥有…，不含…」这类否定式边界；这些由成员类型和所有权表达。
- 领域尺寸不写进类型注释：格子数由 `cells_` 的声明表达，棋盘边长由 `kBoardRows`、`kBoardCols` 表达。
- 枚举与只承载数据的结构体：第一句是名词短语，写这个取值表示什么；需要条件时用 `///<` 补一句可核实的条件。

### 构造函数与析构函数：先写标签，再写职责

特殊成员用标签开头：`默认构造函数：`、`拷贝构造函数：`、`移动构造函数：`、`析构函数：`；其他构造函数写 `构造函数：`。标签后写构造完成后的后置条件，或析构函数负责什么。`= default` 配合成员初始化器建立的不变量，签名上看不见，必须写成后置条件。只写读者能观察到的事实，不写「创建对象」「初始化成员」这类复述。

```cpp
/// 默认构造函数：得到空棋盘，每个格子都是 kEmpty。
///
/// 构造后的状态与调用 `Clear()` 相同，不抛异常。
Board() noexcept;
```

默认构造、析构和 `void` 且无参数的函数写两段：第一段写后置条件或职责，第二段写调用方还要知道的边界；不写空的 `@param`、`@return`。有参数或有返回值的函数按下一节写标签，构造与析构不写 `@return`。标签说明这是哪一类特殊成员，不重复类名；非默认构造同样写建立的不变量与失败方式。

### 数据成员：上一行 `///`，先写名词再写约定

类数据成员的主注释写在声明上一行，统一用 `///`，私有成员也一样。第一句先写这个成员是什么，再在同一句里补类型和名字看不出的约定：轴向、单位、哨兵值、所有权、外部约定、初值含义或改写时机与次序。有补充时写成一句 `/// 名词：约定。`，冒号用全角 `：`，句号结束；修饰必须依附于被修饰的名词，不能单独占一行。行尾不写 `//` 或 `///<`；`///<` 只留给枚举项和 `struct` 的短字段。名字和类型已经说清时不写。

```cpp
/// 棋盘格子数组：外层下标是行，内层下标是列。
std::array<std::array<CellType, kBoardCols>, kBoardRows> cells_{};
/// 当前玩家：开局由 X 先手。
Player current_player_ = Player::kCross;
/// 对局结果：落子被拒时保持原值。
GameResult result_ = GameResult::kInProgress;
```

`board_` 这类名字已经说明存放对象的成员不写「对局棋盘」；`cells_` 不写「存储…」这种把声明读一遍的句子，但上一行要先说它是棋盘格子数组，再补轴向、哨兵和改写次序。`clang-format` 不会把行尾注释搬到上一行，位置由本规则和检查器保证。

### 函数：两段式契约

有参数或有返回值的函数写两段：第一段写结果、失败方式或检查项；第二段按签名把标签写齐。

1. 第一段：普通函数写正常返回什么、失败时返回什么或抛什么；布尔查询与 `operator==` 写「检查…是否…」。
2. 第二段：每个参数一条 `@param`；有返回值就写 `@return`；会抛才写 `@throws`。

```cpp
/// 检查坐标能否落子，不修改棋盘。
///
/// @param position 目标行列坐标。
/// @param cell_type 要放置的棋盘格子类型，必须是 kX 或 kO。
/// @return 可以落子返回 kSuccess；越界、cell_type 为 kEmpty 或目标已有棋子时返回对应拒绝值。
[[nodiscard]] PlaceCellResult CheckPlaceable(CellPosition position, CellType cell_type) const;
```

- 布尔查询与 `operator==`：第一句写「检查…是否…」；`@return` 只写「什么情况下为 true」，再补一句「不检查什么」。条件简单也要写，「名字已经说明」不构成省略理由。
- `@param` 每个参数都写，写范围、单位或所有权，不写「索引」这类同义反复；没有参数就不写空的 `@param`。
- `@return` 每个非 `void`、非构造、非析构的函数都写，写返回值怎么读或失败时返回什么；不要用「见上」或重复第一段。
- `@throws` 必须与 `references/exceptions.md` 一致；不抛异常的函数不写。
- 私有函数同样写契约，不能默认调用者知道前置条件；输出参数标 `[out]`，既读又写标 `[in,out]`。

### 实现：阶段边界与为什么

`.cpp` / `.cc` 里，函数体用 `//`，不用 `///`：体内的 `///` 会接到该函数的 Doxygen 详细说明后面，成为误导性文档。重要函数按空行分段，每一段上方写一句 `//`。句子写边界、失败后果或为什么停在这里，不把下一行条件翻译一遍；`IsWin` 这种单表达式函数不配注释。只写删掉会让下一次修改得到错误结果、而代码本身看不出的内容。

什么时候在 `if` 上方加一句：

- 多条独立拒绝（如 `CheckPlaceable`）：每个 `if` 上一行一句，写拒绝后棋盘怎样。
- 成功写入的上一行一句，写为什么到这里才改棋盘。
- 只有次序依赖的一对 `if`（如 `GetWinner`、`JudgeAfterPlace`）：第一组上方一句说明次序为什么不能反，第二个 `if` 不复制同一句。
- 循环上方已经有阶段说明时，循环里的 `if` 不再加一行。
- `HasLine`、`IsFull` 这类单表达式不加；`GetWinner` 里的次序判断只在它真的解释「为什么先判胜」时留一句。

大型工程的共识是解释意图而不是逐步翻译：[Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html#Implementation_Comments) 要求注释解释代码在做什么，不描述代码本身；[LLVM Coding Standards](https://www.llvm.org/docs/CodingStandards.html#commenting) 要求写意图与理由。阶段注释写的就是这两类信息。

典型位置：

- 次序依赖：先判胜再判满，否则最后一子会变成平局。
- 类型收窄与解析：先按 64 位读再收窄；解析失败后必须丢掉整行。
- 三种拒绝都在赋值前返回，棋盘保持原样。
- 状态不变量、外部格式、回退路径、刻意重复。
- 共享方式：`thread_local` 之类的可见性。

循环体里逐行复述 `push_back`、`return` 的注释一律删；不写变更史、外部资料路径和注释掉的代码。CMake 的契约注释不在这里，写法见 `../../configuring-cmake/references/cmake.md`。

### 长度预算

| 层 | 行数 | 第一句 | 写什么 |
| --- | --- | --- | --- |
| 文件头 | 3–7 | `@file` 文件名 + `@brief` 一句话 | 本文件由哪几部分组成 |
| 类型注释 | 2–14 | 名词短语：这个类型或取值是什么 | 只有类的不变量 |
| 特殊成员 | 1–3 | 标签（默认/拷贝/移动构造函数、析构函数） | 后置条件或职责 |
| 函数注释 | 3–10 | 正常返回什么、失败时返回或抛什么、检查什么 | 每个参数、返回值与失败方式 |
| 无标签函数 | 2 | 两段：后置条件/职责，再补边界 | 仅限构造、析构、`void` 无参数 |
| 数据成员 | 上一行 1 句（`/// 名词：约定`） | 名字和类型看不出的范围、初值含义、轴向或哨兵 | 什么时候变 |
| 实现注释 | 每个空行阶段 1 句 | 边界、失败后果或为什么停在这里 | `//`，只给重要函数 |

## 布局：放在哪一层、哪一行

- `///` 只给声明与文件头：头文件里的类型、函数声明、枚举项、公开与私有数据成员，以及文件头的 `@file`/`@brief` 块。调用方和 Doxygen 从这里取契约。
- `///<` 只给枚举项和 `struct` 短字段的行尾；不要写在赋值、`break` 或普通语句后面。
- `//` 给函数体内的阶段说明、局部变量、守卫理由和普通语句行尾；这些注释不接 Doxygen 文档。
- `//` 也给工具指令与别种文件：`// NOLINTNEXTLINE(...)`、`#endif  // MACRO`，以及 CMake、YAML 等非 C++ 文件。
- 判断看位置：声明写契约，用 `///`；实现写理由，用 `//`。
- 位置固定：文件头在最上方；类型注释紧贴类型声明；特殊成员（构造、析构、拷贝与移动）排在其他函数之前；函数注释紧贴函数声明；数据成员的主注释紧贴声明上一行，不写行尾补充。
- 类数据成员（含私有）的主注释用 `///`；行尾 `///<` 只给枚举项和 `struct` 的短字段。
- 注释和它说明的声明之间不留空行；同一个声明块内，空行只用来分组。

### 文件头

每个手写源文件开头写一段 doxygen 文件头：第一行 `/// @file <文件名>`，第二行 `/// @brief` 一句话说明这个文件定义或实现什么，用一行 `///` 隔开后，只写本文件自己的组成部分或边界。`@file` 的参数必须与文件名逐字相同，检查器会核对。`@brief` 默认写出；`@author`、`@date`、`@copyright`、`@version` 默认不写，只有插件配置里打开并填了非空值才写出，作者、年份和变更史不写进源码。删掉把读者指去另一个头文件、另一个目录或另一层的句子，也删掉「这一层不负责什么」。不写作者、版权年份、变更日志和外部资料路径。

```cpp
/// @file board.h
/// @brief 定义井字棋棋盘、格子坐标与格子类型。
///
/// 棋盘保存九个棋盘格子的状态，提供查询、落子与清空棋盘。
```

- C++ 源文件用以上格式；CMake 用 `#`，YAML/JSON 用 `#`。
- 超过约 200 行的文件用空行分成几节，每节的说明写在一行 `///` 上，不画装饰线。
- 文件头 3–7 行；`@file` 与 `@brief` 各占一行，后面只写本文件的范围与组成，不写实现步骤、作者和变更史。

## 排版：符号、宽度与标签

- 行宽跟项目 `.clang-format` 的 `ColumnLimit` 走（Google 基线是 80 列，中文按两列计）。
- 行尾注释与代码之间空两格；`///<` 只接在枚举项和 `struct` 短字段声明行尾。
- `@param`、`@return`、`@throws` 标签保持英文；`@param` 后先写参数名，再写一句。
- `TODO:` 后先写定位（阶段名或 issue 号），再写一个短横线，再写动作；不写 `TODO(某人)`，不写没有动作的 TODO。
- `.clang-format`、`.clang-tidy`、`.clangd`、CMake 的配置项旁边写「为什么这样设」，不写「这一项是什么」；配置注释贴在被解释的键上方。
- 禁止：大段表格、装饰图案、表情；外部资料路径、跨仓库引用、团队流程；注释掉的代码；注释元叙述（「其余内容见某处」「两处不重复」）。
- `///` 与 `@param` 不进入 `.qmd`、YAML、CSS。
- 函数体内不写 `///`；`//` 用于实现说明与 `// NOLINTNEXTLINE(...)` 这类工具指令。

## 润色：删复述，统一句式

- 类型第一句是名词短语；布尔查询与 `operator==` 用「检查…是否…」；普通函数第一句写结果、失败方式或检查项。
- 特殊成员保留标签（`默认构造函数：`、`析构函数：` 等），但禁止只写「构造函数：创建对象」这类没有后置条件或职责的句子，也禁止复述类名、签名、成员清单。
- 禁止在类型注释里写领域尺寸（3×3、九个格子、边长）；尺寸由成员声明和常量表达。
- 禁止把成员功能清单按声明顺序抄一遍；函数契约写在各自函数上。
- 同一事实只写一处：声明注释、实现注释、书稿和 README 不各讲一遍。
- 删掉注释后读者不会做错事、或注释只重复签名时，删；但写作节要求保留的后置条件、轴向、哨兵和改写时机不在此列。
- 只改注释时仍走第 3、4 步，然后回读：文件头 → 类型（名词短语 + 只有类的不变量）→ 特殊成员（标签 + 后置条件/职责）→ 函数（结果/失败方式/检查项 + 参数）→ 数据成员（只读上一行 `///`：名词 + 全角冒号 + 约定；行尾不应有注释）→ 实现（每个空行阶段的边界或理由）→ 术语与新符号是否真实存在 → 运行 `checking-comments.mjs` 兜底。
- 注释写给维护者，正文写给读者；设计理由、方案比较与算法取舍写在正文或实现注释里，公开接口只留契约。
- 禁止用注释代替类型、`const` 或 `[[nodiscard]]`。
