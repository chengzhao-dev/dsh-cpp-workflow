# 注释

注释分四层：文件头、章节横幅、声明注释、实现注释。配置文件的注释单独一层。每层只写该层该管的事，不互相复制。

## 文件头

每个手写源文件、脚本、配置文件开头写一段文件头：这个文件负责什么、边界在哪里、什么时候需要读它。不要写版权年份、作者、变更日志。

```cpp
//===----------------------------------------------------------------------===//
// Inventory 的存储、边界检查与入库规则。
//
// 不处理终端输入输出；程序层负责把用户输入翻译成 Position。
//===----------------------------------------------------------------------===//
```

- C++ 文件用 `//`，CMake 用 `#`，YAML/JSON 用 `#` 或 `//`（按文件类型）。
- 文件头控制在 6 行以内；不写实现步骤，不写知识库 id 或文档路径。
- 生成文件、第三方文件、纯数据文件可以不写文件头。

## 章节横幅

长文件（超过约 200 行）用横幅分组，组名是读者要跳转的锚点。

```cpp
//===----------------------------------------------------------------------===//
// 构造与生命周期
//===----------------------------------------------------------------------===//
```

- 横幅宽度固定 100 列；`//` 后 3 个 `=`，中间 90 个 `-`，末尾 `===//`。
- 横幅只包住逻辑组，不包住单个函数；函数之间用空行，不用横幅。
- 脚本里用 `#===` 形式，宽度同样 100 列；CMake 用 `#---` 小节即可，不用重横幅。
- 一个文件不超过 8 个横幅；超过说明文件该拆了。
- 100 列换行分三类：整句在标点处断；参数/返回值列表每项一行；代码示例保持原样，宁可横向滚动也不在半句断开。

## 声明注释

公共头文件里的类型、函数、常量用 `///` 写契约，调用方读完就知道怎么用。

```cpp
/// 返回 (row, col) 处的物品状态。
///
/// @param row 行号，必须在 [0, kSlotRows) 内
/// @param col 列号，必须在 [0, kSlotCols) 内
/// @return 该位置的物品状态
/// @throws std::out_of_range row 或 col 越界
[[nodiscard]] ItemState GetItem(int row, int col) const;
```

- 第一行一句话说清「做什么」，空一行后写参数、返回值、异常。
- `@param` 要么全写，要么全不写；只有一个参数且含义自明时可以省略。
- `@return` 在返回类型自明时省略；`[[nodiscard]]` 已经表达「必须使用」时不要再写一遍。
- `@throws` 必须和 `references/exceptions.md` 的合同一致；不抛的函数不要写。
- 禁止 `@todo`、`@fixme`、`@author`、`@since`；待办统一用下面的 TODO 格式。
- 枚举值的尾随注释用 `///<`，全部值都写或全部不写，并对齐；语义结果写在最前，编号或内部值写在后面。
- 私有声明同样写合同：调用者可能是同一个类的另一个成员，不能假设它知道所有前置条件。
- 参数是输出参数时在 `@param` 后标 `[out]`；既读又写时标 `[in,out]`。
- 不写 `@brief`、`@details` 这类空壳标签；第一行本身就是摘要。

## 实现注释

`.cpp` 里的注释只写「为什么」和「这里有什么坑」，不复述语句。

```cpp
// 先判空再取首元素：空订单列表是合法状态，不能假设至少有一单。
if (orders_.empty()) {
  return OrderResult::kInProgress;
}
```

- 不写「遍历 slots_，检查是否超过阈值」这种把下一行翻译一遍的注释。
- 注释放在被解释语句的上方；只有短小的状态说明可以放行尾，且一行只挂一个语句。
- 不要把注释挂在 `if` 和它的 `else` 中间；分支各自的理由写在分支内部上方。
- 一个注释只解释一件事；解释两件事时拆成两行或两个注释。
- 相邻的单行注释合成一个注释块，一行一个要点；不要把整段说明挤进一个长行。
- 处理溢出、越界回退、平台差异时，注释写「为什么这个分支存在」和「不这样会怎样」，不写「这里做了检查」。
- 不写「这里用了 vector 因为……」「这里改成……更好」这类实现史；设计取舍写进提交说明或文档。
- 注释掉的代码不保留；需要时从版本历史取。

## TODO

统一格式：

```cpp
// TODO: 阶段 3 - 支持撤销入库
// TODO: issue #42 - 把边界检查抽到 Inventory
```

- `TODO:` 后先写定位（阶段名或 issue 号），再写一个短横线，再写动作。
- 不写 `TODO(某人)`；人不重要，上下文重要。
- 不写没有动作的 `TODO: 参考 xxx`；要么写清要做什么，要么删掉。
- 提交前搜一遍 `TODO`，能做完的做完，做不完的保留定位。

## 语言与术语

- 注释用中文；标识符、标准库类型、命令、错误消息保持原文。
- 同一个概念只用一种译法；术语表见 `references/glossary.md`。
- 不写「显然」「众所周知」；读者不需要被评判。
- 注释不超过两行连续说明；超过时先问是不是该抽函数或写文档。

## 配置注释

`.clang-format`、`.clang-tidy`、`.clangd`、CMake 的配置项旁边写「为什么这样设」，不写「这一项是什么」。

```yaml
# 团队统一 100 列；80 列在模板和格式化串里换行过碎。
ColumnLimit: 100
```

- 配置注释贴在被解释的键上方，不写大段策略头。
- `.clang-format` 按逻辑组分段，每组一句注释说明这一组在管什么；不要逐键写「设置 X 为 Y」。
- `.clangd` 每个键组一句话，说明为什么需要这个编译数据库或参数；不要复制整份 CMake 配置。
- 不在配置里写 `TODO` 或指向某份文档的路径；配置要能独立读懂。
- `.clang-tidy` 的每个关闭项写一句理由；没有理由的关闭项删掉。
- 同一个理由只写一次，不逐项复制。
- 源码注释不写团队政策或流程；那些属于文档，不属于被阅读的代码。

## 禁止

- 注释里写知识库路径、知识库 id、`bg-` 开头的条目名或项目专属类名。
- 用注释代替类型、`const`、`[[nodiscard]]` 能表达的限制。
- 大段 ASCII 表格、装饰性图案、表情符号。
- 把注释当提交说明或变更日志。
