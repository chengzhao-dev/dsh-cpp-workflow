# 领域建模与项目设计

在写第一个类之前，先决定领域里有哪些值、哪些规则、哪些边界。类型设计错了，后面的命名、注释和测试都只能补救。

## 先找领域值

把需求里的名词分成四类：

| 类别 | 例子 | 表示 |
| --- | --- | --- |
| 数量、标识、尺寸 | 优先级、编号、长度 | 定宽整数或强类型包装 |
| 参与者、角色 | 用户、当前处理人 | `enum class`，取值封闭 |
| 状态、类别 | 待处理、进行中、已完成 | `enum class`，取值封闭 |
| 动作、结果 | 添加、完成、拒绝及原因 | `enum class` 或聚合 `struct` |

- 取值集合封闭时用 `enum class`，不用 `int` 常量或字符串。
- 有多个字段且总是一起传递的值用 `struct` 聚合；需要维护不变量的对象用 `class`。
- 同一底层类型承载不同含义（米/秒、行/列）且容易混用时，用轻量强类型包装。
- 不为每个名词造类；只有出现行为、不变量或独立变化原因时才升级为 `class`。

### 取值的边界

- 封闭取值一次列全。方格的取值是空、X、O；不要把 X 和 O 做成不含空的棋子，再用空表示空方格。
- 位置是行和列，不是方格的另一种取值。胜负、轮到谁、已下过的序列属于对局，不要塞进位置类型。坐标类型单独一个头文件；持有尺寸的类型包含它，不把坐标塞回尺寸类型里。
- 方格只是值容器：默认是空，写入任意取值，后写覆盖前值；是否允许覆盖、何时清空由容器决定。不要给方格加落子、清空或终局判断。
- 一次落子能区分的失败放进结果枚举：玩家不对、对局已结束、值非法、方格已有值。棋盘只做坐标检查与写入，不回答这一手成没成；判断留在对局层。
- 结果枚举跟随产生它的那一层：棋盘没有结果枚举，写入要么完成，要么因越界抛出；落子结果 `PlaceResult` 与整局结果 `GameResult` 都留在对局层。
- 对局层的落子入口返回这一手的 `PlaceResult`，整局结果由 `GetResult()` 另外回答；不要用 `GameResult` 兼答两件事，也不要再包一层只带成败与终局的类型。结果类型按调用方要区分的东西选：无载荷、要区分每种原因时用 `enum class`（如 `PlaceResult`）；缺失不需要第二种原因时用 `std::optional`；成功带载荷或原因时用 `std::expected<T, E>` 或具名 struct；不用 out 参数。选型见 `references/language/value-types/04-enum.md`「什么时候不用枚举」。
- 调用方已经把完整值对象交进来时，下层直接用它，不再用散参数或查询重新拼出同一对象。可以校验，并在不符时返回原因；不要静默替换成自己重算的值。
- 构造值对象所需的只读查询留在拥有状态的一层；调用方用它组值对象，下层函数不重复推导。不要为了去掉查询，让每个调用方各自维护轮次副本。
- 范围检查在接收位置的那一层直接做，越界直接抛出；不要为了统一诊断把 `std::source_location` 穿过每个公共接口。
- 尺寸是某个类型的事实时，写成该类型的 `static constexpr`，例如 `Board::kRowCount`；不要再造一个只做 `static_cast<std::size_t>` 的别名常量。
- 一个局面的结果只用一个枚举和一个查询。不要把满盘、终局和赢家拆成三个入口，再由调用方拼回去。

## 读取边界

- 任务路由表登记到具体文件：声明、实现与测试各写清楚；不登记整个工程目录。目录路由会把几十个无关文件带进上下文，真正要改的格式化器、查询或异常消息反而被淹没。

## 封闭状态与结果

- 状态用连续取值的 `enum class`：`kPending`、`kActive`、`kDone`。
- 状态转换写成显式函数或规则对象，不用一串 `if` 直接改整数。
- “动作是否合法”和“动作执行结果”分开：合法性查询返回 `bool` 或原因，执行返回结果对象。
- 失败是调用方的正常结果（编号不存在、输入格式不对）时用返回值表达；函数无法完成自己的任务、或状态机进入不可能分支时抛异常，规则见 `references/exceptions/01-exception-rules.md`。
- 结果对象携带足够信息让调用方决定下一步；失败原因不止一种时不要只返回 `bool` 再让调用方猜原因。
- 动作只有一个失败原因、调用方也不需要区分时返回 `bool`，`@return` 写清 true 与 false 各自的含义，例如「撤回成功返回 true；没有可撤回的落子时返回 false」；不要为单一失败建只有一个失败取值的枚举。
- 结果枚举先列成功（编号 0），再按固定顺序列失败原因：`kPlaced = 0`、`kInvalidPlayer = 1`、`kFinishedGame = 2`、`kOccupiedSquare = 3`。编号只用来区分结果，不表示检查优先级。
- 每类能区分的失败单独一个取值，不合并成 `kInvalid`；调用方与测试才知道究竟哪条规则拒绝。
- 终局是正常结果项，不抛异常。占用这类「这一手写不进」也返回结果项，由对局层的落子入口一次答清；只有坐标越界仍由棋盘抛出 `std::out_of_range`，因为那是调用方的程序错误，不是对局里的正常分支。
- 调用方穷举枚举时不写 `default`，让 `-Wswitch` 在新增取值时报警告，工程开了 `-Werror` 就是错误。出口不写进 `default`。一个值对多个离散取值分派时用 `switch`；范围比较、布尔组合或只有一两个分支时用 `if`。一个函数里有多条拒绝分支时，每条各写一条独立 `if`，检查不通过就返回；不同拒绝原因互不依赖，不串成 `else if`。成功路径写在函数末尾，不再用 `else` 包住；前面已经提前返回，能走到末尾就说明所有检查都通过。只有一条拒绝分支时同样提前返回，末尾直接写成功路径，不补 `throw` 兜底。

## 规则核心与外围

规则核心只依赖标准库和领域类型：

- 不读终端、不写终端、不碰 GUI、Web、Python 或数据库。
- 不依赖当前时间、随机数种子、环境变量或工作目录；这些由外围注入。
- 输入是领域值，输出是领域结果；文本格式、JSON、HTTP 都在外围转换。
- 核心可以被单元测试直接调用，不需要启动进程或模拟终端。

外围按职责分层：

1. 规则核心：任务集合、状态转换、排序和过滤。
2. 应用层：把一次用户动作翻译成核心调用，把结果翻译成协议。
3. 适配层：终端、JSON 行、HTTP、Python 脚本、GUI。
4. 组装层：`main` 只解析参数、创建对象、连接输入输出。

依赖方向从外向内；核心不知道适配层存在。

## 谁回答这个问题

判断一个操作该落在哪个类型，先看回答它需要哪些数据：

- 需要的数据在哪个类型里，就由那个类型回答（Information Expert）。
- 只有直接碰到内部表示的函数才做成成员；只组合公开查询的函数留在同一命名空间（C.4、C.5）。调用方不另写一份。
- 例外是虚函数、`=`、`()`、`[]`、`->` 这类必须为成员的运算符，以及同一组重载或链式调用里为了接口一致而留下的函数。使用例外时在声明旁写一句原因。
- 示例不指向任何仓库的类：一次落子由对局层接收，因为要同时有坐标、值与轮次；棋盘只检查坐标并写入，不回答占用与终局。对局层掌握参与者、历史与终局，把这一手的结果写成 `PlaceResult`。

## 边界的划分理由

按“变化原因”划分边界，不按文件数量：

- 规则变化（优先级规则、合法动作）和界面变化（提示文案、按钮布局）是两个原因，放两个组件。
- 协议变化（JSON 字段）和规则变化是两个原因，协议转换放应用/适配层。
- 平台变化（Windows/WSL/macOS 路径、动态库查找）放构建脚本或适配层，不进核心。
- 只有调用方应当替换的外部依赖（时钟、随机源、输入输出）才通过接口注入；组件自己规定的策略留在实现里，测试断言可观察结果。

公共头文件只暴露稳定契约；实现细节放 `.cpp` 或私有头。目录形态、扩展名与头文件槽位以 `references/layout/01-source-layout.md` 和 `references/layout/02-file-template.md` 为准。

## 什么时候抽共享库

- 只有第二个真实使用方出现，且两边语义确实相同，才抽共享组件。
- 抽之前先复制，观察两处是否同步变化；如果变化方向不同，说明抽象错了。
- 共享库的公共接口要能独立编译、独立测试；不要为了“复用”把两个领域的类型塞进一个头文件。
- 抽象的理由写进项目技能或设计注释；没有理由的抽象比重复更难维护。

## 规则有歧义时

- 先列出至少两个合理解释，再问用户选哪一个；不要静默选一个继续写。
- 问题要具体到可观察行为：“当两个任务的优先级和截止日期都相同时，按添加顺序还是按名称排序？”
- 用户回答后，把决定写进项目技能的行为表或测试名；下次遇到同一歧义不再猜。
- 不能问时，选更保守的解释（不产生非法状态、不丢信息），并在交付说明里标注假设。

## 函数接口设计

- 一个函数只做一件事；语义不同的动作不要靠默认参数合并。清空整格与清空整盘是两个动作，分别写成 `void ClearSquare(Position pos);` 与 `void Clear();`；不要用 `Clear(std::optional<Position>)` 让调用点猜省略参数的含义。
- 语义不同的动作不要共用名字，也不要靠重载区分（Google：调用点必须能直接看出在调用什么）；重载只用于语义相同的变体。
- 不用 `bool` 参数切换行为；两个分支做不同的事时拆成两个函数，或把开关提成有名字的枚举。
- 参数顺序：被操作的对象在前，控制量与选项在后；输出参数放最后并标 `[out]`。
- 只赋值、不做校验的 setter 返回 `void`，可以标 `noexcept`；不要加 `[[nodiscard]]`，也不要用返回值暗示写入成功。写入是否允许由拥有容器的类型决定，setter 只改值。
- 落子类函数的检查顺序固定为：整局状态 → 本层前置条件（如玩家） → 值合法性 → 坐标（由下层的读取完成） → 占用 → 写入。整局状态不依赖参数，先判断能在对局结束后立刻短路，也不会把「终局后落子」误报成玩家错误；玩家与终局不依赖容器，先判断可省掉无谓的读取；值同样来自参数，先判断可省一次读取。多条拒绝分支按这个顺序各写一条独立 `if`，不串 `else if`；成功路径落在函数末尾。
- 公共接口只保留调用方需要的形态；测试专用的入口不放公共头文件。唯一例外是固定随机源的构造函数：`Computer(Difficulty, std::uint32_t seed)` 与默认构造同义，只在测试里固定随机序列；注释写明用途，不额外暴露内部状态。
- 默认参数只写在声明处；调用点省略参数时，注释要写清省略后的行为，避免「不传 = 全部」成为隐藏约定。

## 撤销与回退

撤销只回退受影响的那一处，不要清空整个容器再重放全部历史。重建的写法时间与空间都是 O(n)，还把简单问题复杂化；能定位到上一处改动的结构，应当直接改那一个元素。

反例（撤回一手却清空整个棋盘，再按历史逐手重放）：

```cpp
board_ = Board{};
for (const Move& move : history_) {
  board_.SetSquare(move.position, PlayerToSquareValue(move.player));
}
```

正例（清空那一格，再把轮次还给落子的一方）：

```cpp
Move last_move = history_.back();
current_player_ = last_move.player;
board_.ClearSquare(last_move.position);
history_.pop_back();
```

棋盘有自己的单格清空接口时直接用它，不要用「清空整个棋盘」代替。

回溯搜索（minimax、走迷宫、试走一步再退回）同样复用「落子 + 撤回」：在同一个对象上推进、递归、撤回，不为每个分支复制整局。复制把 O(1) 的撤回变成 O(n) 的拷贝，搜索树一深就被放大。

## 检查清单

- [ ] 领域值有明确类型，封闭集合用 `enum class`。
- [ ] 规则核心不依赖终端、GUI、Web、Python 或当前环境。
- [ ] 失败是正常结果时用返回值，函数无法完成任务时抛异常；异常类型和捕获方式符合 `references/exceptions/01-exception-rules.md`。
- [ ] 边界按变化原因划分，依赖方向从外向内。
- [ ] 共享抽象有第二个真实使用方和明确理由。
- [ ] 规则歧义已问清或记录了保守假设。
- [ ] 函数只做一件事；同一动作用默认参数合并，语义不同的动作用不同名字；没有 `bool` 开关参数。
- [ ] 回退只改受影响的一处，不清空容器重放全部历史。
- [ ] 回溯搜索复用落子与撤回，不在每个分支复制整局。

## 依据

- [C++ Core Guidelines: Interfaces](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#s-interfaces)：把接口与实现分开，规则与不变量写在接口上，依赖方向从外向内。
- [C++ Core Guidelines: Philosophy](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#s-philosophy)：用类型表达意图，避免裸值穿过边界。
- [Google C++ Style Guide: Classes](https://google.github.io/styleguide/cppguide.html#Classes)：让类保持小而职责清楚，接口只暴露调用方需要的行为。
- [Google C++ Style Guide: Function Overloading](https://google.github.io/styleguide/cppguide.html#Function_Overloading)：重载只用于语义相同的变体，调用点必须能直接看出在调用什么。
- [C++ Core Guidelines: F.51](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rf-default-args)：有选择时优先默认参数，避免为同一语义写多份重载。
- [cppreference: Default arguments](https://en.cppreference.com/w/cpp/language/default_arguments)：默认参数在调用点生效，后续声明不能重复默认值。
