# 领域建模与项目设计

在写第一个类之前，先决定领域里有哪些值、哪些规则、哪些边界。类型设计错了，后面的命名、注释和测试都只能补救。

## 先找领域值

把需求里的名词分成四类：

| 类别 | 例子 | 表示 |
| --- | --- | --- |
| 数量、标识、尺寸 | 优先级、编号、长度 | 定宽整数或强类型包装 |
| 参与者、角色 | 用户、当前处理人 | `enum class`，取值封闭 |
| 状态、类别 | 待处理、进行中、已完成 | `enum class`，取值封闭 |
| 动作、结果 | 添加、完成、拒绝及原因 | `enum class` 或聚合 `struct` |

- 取值集合封闭时用 `enum class`，不用 `int` 常量或字符串。
- 有多个字段且总是一起传递的值用 `struct` 聚合；需要维护不变量的对象用 `class`。
- 同一底层类型承载不同含义（米/秒、行/列）且容易混用时，用轻量强类型包装。
- 不为每个名词造类；只有出现行为、不变量或独立变化原因时才升级为 `class`。

## 封闭状态与结果

- 状态用连续取值的 `enum class`：`kPending`、`kActive`、`kDone`。
- 状态转换写成显式函数或规则对象，不用一串 `if` 直接改整数。
- “动作是否合法”和“动作执行结果”分开：合法性查询返回 `bool` 或原因，执行返回结果对象。
- 可预期失败（编号不存在、输入格式不对）用返回值表达；违反合同（下标越界、状态机不可能分支）才抛异常。
- 结果对象携带足够信息让调用方决定下一步，不要只返回 `bool` 再让调用方猜原因。

## 规则核心与外围

规则核心只依赖标准库和领域类型：

- 不读终端、不写终端、不碰 GUI、Web、Python 或数据库。
- 不依赖当前时间、随机数种子、环境变量或工作目录；这些由外围注入。
- 输入是领域值，输出是领域结果；文本格式、JSON、HTTP 都在外围转换。
- 核心可以被单元测试直接调用，不需要启动进程或模拟终端。

外围按职责分层：

1. 规则核心：任务集合、状态转换、排序和过滤。
2. 应用层：把一次用户动作翻译成核心调用，把结果翻译成协议。
3. 适配层：终端、JSON 行、HTTP、Python 脚本、GUI。
4. 组装层：`main` 只解析参数、创建对象、连接输入输出。

依赖方向从外向内；核心不知道适配层存在。

## 边界的划分理由

按“变化原因”划分边界，不按文件数量：

- 规则变化（优先级规则、合法动作）和界面变化（提示文案、按钮布局）是两个原因，放两个组件。
- 协议变化（JSON 字段）和规则变化是两个原因，协议转换放应用/适配层。
- 平台变化（Windows/WSL/macOS 路径、动态库查找）放构建脚本或适配层，不进核心。
- 测试需要替换的外部依赖（时钟、随机源、输入输出）通过接口注入，不在核心内部直接调用。

公共头文件只暴露稳定契约；实现细节放 `.cpp` 或私有头。一个组件一个 `CMakeLists.txt`，组件的 `include/` 是对外接口，`src/` 是实现。

## 什么时候抽共享库

- 只有第二个真实使用方出现，且两边语义确实相同，才抽共享组件。
- 抽之前先复制，观察两处是否同步变化；如果变化方向不同，说明抽象错了。
- 共享库的公共接口要能独立编译、独立测试；不要为了“复用”把两个领域的类型塞进一个头文件。
- 抽象的理由写进项目技能或设计注释；没有理由的抽象比重复更难维护。

## 规则有歧义时

- 先列出至少两个合理解释，再问用户选哪一个；不要静默选一个继续写。
- 问题要具体到可观察行为：“当两个任务的优先级和截止日期都相同时，按添加顺序还是按名称排序？”
- 用户回答后，把决定写进项目技能的行为表或测试名；下次遇到同一歧义不再猜。
- 不能问时，选更保守的解释（不产生非法状态、不丢信息），并在交付说明里标注假设。

## 检查清单

- [ ] 领域值有明确类型，封闭集合用 `enum class`。
- [ ] 规则核心不依赖终端、GUI、Web、Python 或当前环境。
- [ ] 可预期失败用返回值，合同违反才抛异常。
- [ ] 边界按变化原因划分，依赖方向从外向内。
- [ ] 共享抽象有第二个真实使用方和明确理由。
- [ ] 规则歧义已问清或记录了保守假设。
