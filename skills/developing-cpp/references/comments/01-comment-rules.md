# 注释：写什么

注释按内容、结构、版式、措辞四节组织。本文件写内容：哪些事实值得写、该落在文件头、类型、函数还是实现注释里；结构、版式与措辞见同目录的 `02-style.md`。位置越靠外，越讲概念与契约；越靠里，越讲实现理由。同一件事只写一次。

四域不是四个步骤：操作决定从哪一步进，域决定这次改哪一层；两者的边界与次序见 `../../../shared/operations.md`。本节只写注释里的落点。

按四类改动查：内容决定写什么，结构决定放哪一层哪一行，版式决定符号、宽度与标签，措辞删复述、统一句式。四步都可能删句子，但后置条件和成员约定只有内容能定，措辞不得以「精简」为由删掉。

用词与术语见 `references/comments/glossary/01-comment-terms.md`：判不准时再开。

## 内容：只写声明里看不出的事实

- **第一句先写结果、保证或成立条件**：类型用名词短语写它是什么；普通函数写正常返回什么、失败时返回什么或抛什么；布尔查询写「主体是否状态」，句中有「是否」，句首不用「检查」「判断」「校验」「验证」，`operator==` 写「相等运算符。」。第一句不写「返回 true/false」；`@return` 仍要写明成立时返回 true、不成立时返回 false。条件、参数与实现理由放第二句以后。
- **不写否定式能力边界**：注释不列「不检查…」「不校验…」「不负责…」「不判断…」这类清单；只写本函数保证什么、调用方必须满足什么。前置条件写成「调用方保证…」「仅接受…」或 `@pre`，布尔查询只写成立条件。状态结果可以说「不做修改」「保持不变」，因为它描述的是这次调用的结果，不是能力范围。`scripts/checking-comments.mjs` 会报 `negative-scope`。
- 公共注释回答「这是什么」和「调用方必须遵守什么」；实现注释回答「为什么这样写」和「边界在哪里」。设计取舍、方案对比与演进历史写到书稿、README 或提交说明。
- 用中文散文写完整句子，句号结尾；标识符、标准库类型、`@param` 这类标签保持原文。
- 写之前三问：删掉这句，读者会误解设计或做错事吗？这句只是复述签名或代码吗？这个限制能不能由类型、`const` 或 `[[nodiscard]]` 表达？第一问为否就删，第二问为是就删，第三问为是就改代码。
- 命名、分文件、`enum class`、异常与结果类型这类全项目风格约定只写进项目文档与读者正文；注释不替项目解释风格。
- 状态结论必须带成立条件。「终局后空格仍在」没有说清哪种终局；写成「一方已三连而棋盘尚未占满时，空格仍然留着；平局时棋盘已满，没有空格」。删掉前提换来的短，不算润色。

### 类型：名词短语与不变量

对象是类、结构体、枚举和类型别名。第一句是名词短语：类写「这个类型是什么」，可用全角冒号补更具体的说明；初始状态只在类有不变量时写进第二段，纯值容器归默认构造函数。纯数据结构和枚举写「这个取值表示什么」。

只有类有不变量，且不重复领域尺寸时，才加第二段。第二段直接写不变量与生命周期：初始状态、状态迁移、清空条件；生命周期写在类注释，不拆到成员注释。纯值容器只写一句名词短语：初始状态归默认构造函数，写入与清空条件归对应函数。第二段用概念句写生命周期，不点成员函数名；初始状态、写入条件与清空条件各自独立时各自成段，用一行 `///` 隔开；后一句依赖前一句、共同说明同一生命周期时写成一段，不用逗号把独立条件串成一句。不加「限制：」这类标签，也不写「这一层不负责什么」。纯数据结构和枚举不写第二句。

```cpp
/// 棋盘。
class Board {
```

禁止事项：

- 不写成员清单，不按声明顺序复述接口。函数各自的契约写在函数上。连 `Place`、`Clear` 这样的成员名也不写进类注释；生命周期用「空方格才能写入」这类概念句。
- 不写「至多成功一次」「最多放置一次」这类次数结论：`Clear` 或清空之后状态可以再次变化，次数结论会失效；写当前操作与清空条件，例如「空方格才能放置；清空后才能再次放置」。
- 不写跨类分工。边界靠类型与所有权表达，注释只写本类型保证什么。
- 不写类型系统已经表达的性质（`值语义`、`所有查询都是 const`）。
- 不写尚未发生的用法、方案对比与取舍论证、广告句。
- 纯数据结构不写「只保存…，不拥有…，不含…」这类否定式边界；这些由成员类型和所有权表达。
- 领域尺寸不写进类型注释：方格数由 `squares_` 的声明表达，棋盘边长由 `kRowCount`、`kColumnCount` 表达。
- 枚举与只承载数据的结构体：第一句是名词短语，写这个取值表示什么。状态枚举写「棋盘状态。」，取值枚举写「方格的值。」，结果枚举写「放置结果。」或「一次落子的结果。」这类「<操作>的结果」；不用「表示…结果。」开头，也不写成「方格的状态。」「对局的结果。」这种把所有者塞进短语的写法。行尾 `///<` 的句式见「枚举项与 `struct` 短字段：两种句式」。

### 构造函数与析构函数：先写标签，再写职责

特殊成员用标签开头：`默认构造函数：`、`拷贝构造函数：`、`移动构造函数：`、`析构函数：`；其他构造函数写 `构造函数：`。标签后写构造完成后的后置条件，或析构函数负责什么。`= default` 配合成员初始化器建立的不变量，签名上看不见，必须写成后置条件。只写读者能观察到的事实，不写「创建对象」「初始化成员」这类复述；「初始化为空方格」这类具体状态不算复述。

```cpp
/// 默认构造函数：初始化为空棋盘。
Board() = default;
```

默认构造与析构可以只写一行：标签后直接写后置条件或职责。`= default` 的后置条件写在标签那一行就够，不再另起一段写「不抛异常」，也不为了注释加 `noexcept`。无参数、无返回值的动作只在签名看不出结果时再写一句，不把「不抛异常」当成这句；不写 `@throws` 就表示不抛。默认构造函数要写出具体的初始状态，如「初始化为空方格」「初始化为空棋盘」「初始化为空对局」；「建立初始状态」看不出具体值，不写。对象由多个成员组成时，写整个对象的初始状态，不逐项罗列成员。不写空的 `@param`、`@return`。有参数或有返回值的函数按下一节写标签，构造与析构不写 `@return`。标签说明这是哪一类特殊成员，不重复类名；非默认构造同样写建立的不变量与失败方式。

### 数据成员：上一行 `///`，先写名词再写约定

类数据成员的主注释写在声明上一行，统一用 `///`，私有成员也一样。第一句先写这个成员是什么，再在同一句里补类型和名字看不出、只属于这个成员的约定：轴向、单位、哨兵值、所有权、外部约定。初值含义、状态迁移与清空规则若属于类级不变量，写在类注释，成员注释不重复；成员注释保持一句，名字和类型已经说清时可以不写。

有补充时写成一句 `/// 名词：约定。`，冒号用全角 `：`，句号结束；修饰必须依附于被修饰的名词，不能单独占一行。行尾不写 `//` 或 `///<`；`///<` 只留给枚举项和 `struct` 的短字段。同一个类的成员注释取同一种句式：要么都只写名词，要么都写成 `名词：约定`；不留「有的带冒号、有的只写定语」的混排。注释正文用领域词（`X 玩家`、`O 玩家`），不写 `kX`、`kO` 这类枚举名；枚举名只出现在 `@param`、`@return`、`@retval` 与代码里。

```cpp
/// 方格数组：按行优先排列。
std::array<Square, kSquareCount> squares_{};
/// 当前玩家：开局由 X 玩家落子。
Player current_player_{Player::kX};
/// 落子历史：按落子先后保存。
std::vector<Move> history_{};
```

类有不变量时生命周期写在类注释；纯值容器的初始状态归默认构造函数，成员注释只留这个成员是什么：

```cpp
/// 方格：保存一个 `SquareValue` 的值容器。
class Square {
  /// 方格的值。
  SquareValue value_{SquareValue::kEmpty};
};
```

`board_` 这类名字已经说明存放对象的成员不写「对局棋盘」，也不写「当前棋盘」：时间词只留给确实随时间变化的成员，如 `current_player_` 写「当前玩家」；`squares_` 不写「存储…」这种把声明读一遍的句子，但上一行要先说它是棋盘方格数组，再补轴向与哨兵。`clang-format` 不会把行尾注释搬到上一行，位置由本规则和检查器保证。

### 枚举项与 `struct` 短字段：两种句式

枚举项与只承载数据的 `struct` 短字段用行尾 `///<`，同一枚举各行的 `///<` 对齐。枚举类型注释写枚举负责的对象：`Player` 写「玩家。」，`SquareValue` 写「方格的值。」，`GameResult` 写「对局结果。」，`PlaceResult` 写「一次落子的结果。」；不把类型注释改写成「对局的一方」。

- 行尾短句：`SquareValue` 写 `///< 空`、`///< X`、`///< O`；`GameResult` 写 `///< 棋盘上 X 已连成一线，X 赢下这一局`。
- 结果加说明：以结果类别开头，冒号后按固定顺序写「对局状态 → 落子玩家 → 目标方格」，某一项不适用时省略，不把「方格…」放到句首。如 `///< 成功：落子玩家是当前玩家，值已写入方格`、`///< 失败：目标方格已有值，没有写入`。类型注释已经交代的共同后果（如「没有写入」）不在每一项重复。
- 短字段写「字段：说明」：冒号前是字段的中文名，冒号后补名字看不出的语境，如 `///< 落子位置：棋盘上的行列坐标`、`///< 落子玩家：游戏中的玩家`；只补默认值或单位时用逗号，如 `///< 行号，默认值为 0`。

行尾短句不收句号。结果行与短字段行用全角 `：`：结果行冒号前写结果类别（成功、失败，或带主体的「落子成功」「落子失败」），短字段行冒号前写字段名；冒号后写这次调用的结果与原因，或字段名看不出的语境，两侧都不能为空。不写「X 成线。」「尚未结束。」这类没有主体、只有谓语的片段；禁止空冒号（`///< 成功：。`）、禁止把说明写在类别前面。无冒号的行尾是一句完整的话，可以有句内逗号；有冒号时不得用逗号代替冒号。同一枚举要么每一项都写 `///<`，要么都不写。

### 函数：两段式契约

有参数或有返回值的函数写两段：第一段写结果、失败方式或成立条件；第二段按签名把标签写齐。

1. 第一段：普通函数写正常返回什么、失败时返回什么或抛什么；布尔查询写「主体是否状态」，句中有「是否」，句首不用「检查」「判断」「校验」「验证」，`operator==` 写「相等运算符。」。
2. 第二段：每个参数一条 `@param`；有返回值就写 `@return`；会抛才写 `@throws`；`@pre`、`@post`、`@retval`、`@tparam`、`@note`、`@see` 出厂开关打开；只在确有需要时写，不需要可在设置里关掉。

```cpp
/// 执行一次落子。
///
/// 依次检查对局状态、玩家与目标方格；全部通过才写入棋盘、
/// 记录历史并轮换玩家。任一检查不通过时对局不变。
///
/// @param move 要执行的落子。
///
/// @retval kPlaced 成功：落子玩家是当前玩家，值已写入方格
/// @retval kInvalidPlayer 失败：落子玩家不是当前玩家，没有写入
/// @retval kFinishedGame 失败：对局已经结束，没有写入
/// @retval kOccupiedSquare 失败：目标方格已有值，没有写入
/// @throws std::out_of_range 对局进行中且行或列超出棋盘时抛出。
[[nodiscard]] PlaceResult Place(Move move);
```

- 布尔查询：第一句写「主体是否状态」，句中有「是否」，句首不用「检查」「判断」「校验」「验证」；`operator==` 写「相等运算符。」，第二句写「当…时返回 true」。`@return` 写成「成立时返回 true；不成立时返回 false」，不写「否则」省略后半句。`Is`、`Has` 开头的名字与 `bool` 返回类型已经把成立条件说清时也要写 `@return`，不省略。
- `@param` 每个参数都写，写范围、单位或所有权，不写「索引」这类同义反复；没有参数就不写空的 `@param`。会检查并抛出的参数写「要检查/读取/更新的坐标」，不把「棋盘内」当前置条件。
- `@return` 默认写，写返回值怎么读或失败时返回什么；返回类型与函数名已把条件说清时也要写，不要用「见上」或重复第一段。
- 查询函数（`Get` 开头）：第一句写「获取…」；`@return` 列出可能取到的值，枚举值在 `///` 里用反引号，例如 `kEmpty`、`kX` 或 `kO`。返回副本时第一句和 `@return` 都写「副本」，不写「该位置的方格」这类可读成引用的句子。
- 函数摘要不写参数名：第一段用「指定坐标」「传入的值」「这一步落子」这类语义名词，`pos`、`value`、`move` 等名字只在 `@param` 行出现。`@param` 描述里可以写 `kX`、`kO`、`kEmpty` 这类枚举值，枚举值本身是契约的一部分；签名、调用示例和类图里的参数名属于接口，不在此限。
- 返回多个明确结果（如 `PlaceResult`、`GameResult`）时用 `@retval`，每个值一行，值与说明之间空一格，不做列对齐（一行一项是本工作流的要求；Doxygen 会把相邻的 `\retval` 合成一段，但每项说明仍另起一行，clang-format 不维护标签列宽）；只有一个返回值时用 `@return`，不把几种结果压进一句 `@return`。`@retval` 的说明写这个值何时返回：成功项写「成功：…」，失败项写「失败：…」，冒号后按「对局状态 → 落子玩家 → 目标方格」的顺序写，与枚举行尾注释说法一致即可，不要求逐字相同。
- 更新函数：第一段写动作，第二段写清楚何时更新、什么时候不改；多个结果用 `@retval`，每个值一行，成功项写在最前，其余按固定顺序；描述与标签组之间空一行；参数、返回值、异常、说明各成一组，组与组之间空一行，同一组内的标签连续。这个固定顺序由 `@retval` 的排列表达，不用 `@note` 复述；`@note` 只写调用方额外要知道的运行时风险或前提。会抛的诊断函数（如 `ValidatePosition`）第一句写「……时抛出 `std::out_of_range`」，不写「……是否……」。
- `@throws` 必须与 `references/exceptions/01-exception-rules.md` 一致；不抛异常的函数不写。
- 私有函数同样写契约，不能默认调用者知道前置条件；输出参数标 `[out]`，既读又写标 `[in,out]`。
- 函数注释不写本函数被哪些成员调用：调用关系会随重构过期，契约只写这个函数做什么、参数、返回值与异常；需要说明协作时写前置条件或后置条件，不点名其他成员。
- `std::formatter<T>` 特化的 `parse` 与 `format` 也按本节写：`parse` 写接受的格式与失败方式，`format` 写「把…格式化后写入输出上下文」这类职责句；具体输出形态由测试与读者正文承担，不重复进源码注释；不因为位于模板特化里就省略。

### 实现：阶段边界与为什么

`.cpp` / `.cc` 里，函数体用 `//`，不用 `///`：体内的 `///` 会接到该函数的 Doxygen 详细说明后面，成为误导性文档。重要函数按空行分段，每一段上方写一句 `//`。`//` 里的枚举值不包反引号，反引号只留给声明注释；一句赋值、单表达式函数（如 `IsEmpty`）不写注释；与 `if` 同义的「检查…是否…」不写，分支结果交给 `return`、`throw` 或赋值。只有次序依赖、恢复现场、调用方保证或防御分支的理由才写一句。局部值是上一行赋值取出、赋值与上一个阶段之间又有空行时，注释写在赋值那一行上方，说明赋值与紧随其后的分支这整块；`if` 上不再重复同一句。只写删掉会让下一次修改得到错误结果、而代码本身看不出的内容。

拒绝与写入分支默认不写注释：`return`、`throw` 或赋值已经说明结果。

```cpp
// 先判终局，再判玩家与方格：失败结果的优先级由此决定。
if (!IsInProgress()) {
  return PlaceResult::kFinishedGame;
}
```

- 只有次序依赖、恢复现场、调用方保证或防御分支的理由才写一句；不写与 `if` 同义的「检查…是否…」。
- 分支只检查紧邻上一行取出的元素（如 `Square& square = ...` 后的 `if (!square.IsEmpty())`）时，说明写在取元素那一行上方；`if` 上不重复，赋值与 `if` 之间也不留注释。
- 不写「目标方格已有值时不覆盖。」这类把分支后果复述一遍的句子。
- 防御性分支写一句为什么这里还要判；没有真实防御分支时不硬加。
- 多条独立拒绝（如 `Game::Place`）不逐条注释；只有失败结果的优先级需要说明时，在第一条 `if` 上方写一句总起。
- 一个 `if` 有多个条件时，按代码的判定顺序写：先确认的条件在前，后核对的在后。如 `// 先确认第一个方格有值，再核对三个方格的取值是否相同。`
- 成功路径含多步状态更新（记录这一步、轮到对方、计数）时，在第一步上方用一句阶段注释概括整段；不在每一步上方逐行解释。
- 阶段注释用读者看得懂的词：不写「换手」「记入历史」这类内部简称；写清对象与动作，如「记录这一步并轮到对方」。短注释也要能独立读懂，不能靠上下文猜。
- 只有次序依赖的一对 `if`（如 `GetWinner`、`JudgeAfterPlace`）：第一组上方一句说明次序为什么不能反，第二个 `if` 不复制同一句。
- 循环上方已经有阶段说明时，循环里的 `if` 不再加一行。
- `HasLine`、`IsInRange` 这类单表达式不加；`GetWinner` 里的次序判断只在它真的解释「为什么先判胜」时留一句。
- 头文件里已经声明的函数，定义处不再写 `///`；只在 `.cpp` 出现、且有参数或返回值的函数，在定义上一行写与头文件声明相同的完整契约（`@param`、`@return`、`@pre` 等）。类方法的定义不重复声明处的注释；没有参数与返回值的 `.cpp` 局部函数可以只写一句用途。
- 函数体里的关键局部声明（查表、分派表、缓存）上方写一句它是什么、覆盖哪些情况；表项内部的分组注释保留，不逐行翻译。

大型工程的共识是解释意图而不是逐步翻译：[Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html#Implementation_Comments) 要求注释解释代码的意图与理由，逐行复述代码是反例；[LLVM Coding Standards](https://www.llvm.org/docs/CodingStandards.html#commenting) 要求写代码想做什么与为什么，不写微观做法。阶段注释写的就是这两类信息。

中文句式按 GB/T 15834-2011《标点符号用法》4.4.3.1（复句内分句之间用逗号）、4.1.3.1（句号用于句子末尾）与阮一峰《中文技术文档的写作规范》（主动句、主语明确、句子短）写；与 NL.1「不在注释里重复代码」的张力，用「分支结果交给 `return`/`throw`，只保留次序或防御理由」消解。

典型位置：

- 次序依赖：先判胜再判满，否则最后一子会变成平局。
- 类型收窄与解析：先按 64 位读再收窄；解析失败后必须丢掉整行。
- 三种拒绝都在赋值前返回，棋盘保持原样。
- 状态不变量、外部格式、回退路径、刻意重复。
- 共享方式：`thread_local` 之类的可见性。
- 关键局部表：表覆盖哪几类情况、编号按什么顺序；表项不再逐行解释。

循环体里逐行复述 `push_back`、`return` 的注释一律删；不写变更史、外部资料路径和注释掉的代码。CMake 的契约注释不在这里，写法见 `../../../engineering/references/cmake/targets/01-target-rules.md`。

### 长度预算

| 层 | 行数 | 第一句 | 写什么 |
| --- | --- | --- | --- |
| 文件头 | 3–7（实现文件 2） | `@file` 文件名 + `@brief` 一句话 | 本文件由哪几部分组成 |
| 类型注释 | 1–14 | 名词短语：这个类型或取值是什么 | 纯值容器 1 句；只有类的不变量与生命周期才写第二段 |
| 特殊成员 | 1–3 | 标签（默认/拷贝/移动构造函数、析构函数） | 后置条件或职责 |
| 函数注释 | 3–10（按标签数放宽） | 正常返回什么、失败时返回或抛什么、成立条件 | 每个参数、返回值与失败方式 |
| 无标签函数 | 2 | 两段：后置条件/职责，再补边界 | 仅限构造、析构、`void` 无参数 |
| 数据成员 | 上一行 1 句（`/// 名词：约定`） | 这个成员是什么；只属于它的轴向、哨兵或所有权 | 只写成员自身，不重复类注释的初值与状态迁移 |
| 实现注释 | 每个空行阶段 1 句 | 边界、次序或防御理由 | `//`，只给重要函数 |

## 依据

- [Google C++ Style Guide: Comments](https://google.github.io/styleguide/cppguide.html)：声明注释写用途与用法，定义注释写实现行为；类、函数、实现注释分层。
- [C++ Core Guidelines: NL.1–NL.3](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#s-naming)：NL.1 不在注释里重复代码能说清的事；NL.2 注释写意图；NL.3 注释保持可读。
- [LLVM Coding Standards: Commenting](https://llvm.org/docs/CodingStandards.html#commenting)：写代码想做什么与为什么，不写微观怎么做；公共接口不重复签名已能推断的信息。
- [Doxygen: Documenting the code](https://www.doxygen.nl/manual/docblocks.html)：`///` 与 `/** */` 的文档块、brief/detailed 分段。
- [Doxygen: Special commands](https://www.doxygen.nl/manual/commands.html)：`@param`、`@return`、`@retval`、`@pre` 等命令的用法与分组。
- [Microsoft: XML documentation comments](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/)：摘要、参数、返回值与异常标签的写法。
- [Microsoft: Recommended XML tags](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/recommended-tags)：`<summary>`、`<param>`、`<returns>`、`<exception>` 等推荐标签。
- [Oracle: Javadoc Doc Comment Specification](https://docs.oracle.com/en/java/javase/21/docs/specs/javadoc/doc-comment-spec.html)：文档注释的结构、标签顺序与可读性。
- [Google: API reference comments](https://developers.google.com/style/api-reference-comments)：API 参考注释的句式、摘要与参数说明。
- [PEP 257](https://peps.python.org/pep-0257/)：文档字符串的摘要行、空行与参数说明。
- [rustdoc: How to write documentation](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)：文档注释的摘要、段落、示例与链接。
- [Go: Doc Comments](https://go.dev/doc/comment)：文档注释的句式、段落与列表。

本工作流的取舍：注释写在赋值上方而不是 `if` 上方，属于项目约定；判断「这句该不该写」的标准是删掉不会让下一次修改出错就不写；`@retval` 一行一项也是项目要求，Doxygen 只规定相邻 `\retval` 的合并方式。

注释里的「方格」「值」用词见 [01-comment-terms.md](glossary/01-comment-terms.md)。
