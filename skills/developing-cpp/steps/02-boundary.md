# 第 2 步：定边界

## 产出

一张边界表：每个组件放什么、哪些头文件是公共接口、库 target 依赖什么、程序 target 依赖什么。还要写清终端输入输出放在哪里。

```text
<component>/include/<name>.h   公共接口
<component>/src/<name>.cpp     实现
tests/                         测试
app                            只做参数、输入输出和装配
```

## 通用情况

- 库 target 不依赖终端、GUI、网络脚本或全局单例；它只接收值、返回值、抛合同异常。
- 程序 target 链接库，负责读参数、读标准输入、打印结果、把退出码翻译成进程退出码。
- 公共头文件直接放在组件的 `include/` 根下，用裸文件名包含；不要写 `#include "<component>/x.h"`。
- 依赖方向从程序指向库。库不反向包含程序的 `cli.h`，也不引用 `main.cpp`。
- 测试放 `tests/`，测试 target 链接被测库；测试不复制库的实现。
- 只有一个可执行文件、没有复用需求时，可以不分库；一旦出现第二个调用方或测试需要直接调用，再拆库。
- 抽共享库前先确认第二个真实使用方和相同语义；只是“看起来会复用”不构成理由。抽象理由写进项目技能或设计注释。
- 第 2 步不写 `CMakeLists.txt`。只决定边界，构建 target 留给 `building-cpp` 的第 5 步。

## 情况

**单文件程序**：`src/main.cpp` 可以有 `main()` 和私有辅助函数；一旦辅助逻辑需要测试，把它移到库组件。

**领域核心 + 外围**：规则核心（状态、合法性、胜负/结果）只依赖标准和领域类型；终端、GUI、Web、Python、Quarto 都在适配层。依赖方向从外向内，核心不知道适配层存在。

**库 + 程序**：库放在 `<component>/`，程序放在 `app/` 或根 `src/main.cpp`；程序只包含库的公共头。公共头只暴露稳定契约，实现细节放 `.cpp` 或私有头。

**静态库 / 动态库**：接口相同，差别在链接方式和运行时库路径；都遵守「库不依赖终端」。选哪种由第 5 步的构建需求决定。

**测试**：测试通过公共头调用库，不包含 `src/` 私有头；需要测私有逻辑时，先判断它是否应该成为公共行为。

## 正反例指针

- 终端输出被塞进库、程序反向依赖：`examples/structure.md`「边界」。
- 公共头放在 `src/`、用带组件前缀的包含路径：`examples/structure.md`「头文件位置」。
