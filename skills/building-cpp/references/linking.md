# 从源文件到可执行文件

链接错误和编译错误是两类问题。先判断失败发生在哪个阶段，再改对应的文件。

## 四个阶段

```text
预处理  ->  编译  ->  汇编  ->  链接  ->  加载运行
.i         .s / .o             可执行文件 / 库
```

- 预处理：展开 `#include`、宏和条件编译，得到翻译单元。头文件找不到在这一步失败。
- 编译：把翻译单元变成目标文件，做语法、类型和模板检查。函数体错误在这一步失败。
- 汇编：把汇编文本变成目标文件；通常由编译器驱动。
- 链接：把多个目标文件和库合并，解析符号引用。`undefined reference` 在这一步失败。
- 加载：程序启动时由动态加载器找到共享库；`error while loading shared libraries` 在这一步失败。

`g++ -c file.cpp` 只编译不链接；`g++ file.o -o app` 只链接。`-E` 只看预处理，`-S` 只看汇编。

## 头文件、声明与定义

- `#include` 是文本替换，不是模块导入；头文件只放声明、`inline` 定义、模板和 `constexpr` 定义。
- 普通函数的定义放 `.cpp`；在头文件里写非 `inline` 函数定义，多个翻译单元包含时会重复定义。
- 类定义放头文件；成员函数在类外定义时写 `ClassName::`，定义放 `.cpp`。
- 只用到声明时不要包含完整定义；前置声明可以减少编译依赖，但不能替代需要完整类型的场景（继承、成员对象、按值返回）。
- 每个头文件自包含：单独编译一个只包含该头文件的 `.cpp` 应通过。用路径式 `#define` 守卫防止重复包含，不用 `#pragma once`。

## `undefined reference` 分诊

| 现象 | 常见原因 | 修法 |
| --- | --- | --- |
| 链接器说某个成员函数未定义 | 声明了但没写定义，或 `.cpp` 没加入 target | 补定义，或把源文件加入 `target_sources` |
| 只有某个平台失败 | 条件编译把定义排除了 | 检查宏和平台分支，保证每个平台都有定义 |
| 第三方库符号缺失 | 没链接库，或库顺序不对 | `target_link_libraries` 加库；CMake 会处理顺序 |
| C++ 符号被当成 C 符号 | 头文件缺少 `extern \"C\"` | C 接口头加 `extern \"C\"`，C++ 调用方也可见 |
| 模板成员未定义 | 模板定义在 `.cpp`，实例化点看不到 | 模板定义移到头文件，或显式实例化 |
| 静态库中的目标文件没被拉入 | 链接器只取被引用符号所在的目标文件 | 确认符号确实被引用，或改用对象库/共享库 |

先看链接器报的完整符号名和来源文件，不要只看第一行。

## 静态库与共享库

| 形式 | 产物 | 链接时机 | 运行期依赖 | 适用 |
| --- | --- | --- | --- | --- |
| 静态库 | `libname.a` | 链接时复制所需目标文件 | 无 | 分发简单、启动快、库小 |
| 共享库 | `libname.so` / `.dylib` / `.dll` | 链接时只记录依赖 | 运行时要能找到库 | 多程序共享、插件、独立升级 |

- 静态库不是“把源码打包”；它仍是多个目标文件的归档，链接器按需取用。
- 共享库的符号默认可能被导出；需要隐藏内部符号时设置可见性（`-fvisibility=hidden` + 显式导出）。
- 共享库的 ABI 包括类布局、虚表、标准库类型和编译器选项；不同编译器或 `-stdlib` 混用可能链接成功但运行崩溃。
- 一个项目里不要同时链接两套标准库（libstdc++ 与 libc++）；编译器、clangd、库和可执行文件必须一致。

## 输出目录与 RPATH

推荐布局：

```text
build/<compiler>/
  bin/app
  lib/libgame.so
  compile_commands.json
```

- 可执行文件在 `bin/`，共享库在 `lib/`；不要把库和可执行文件混在同一层。
- 运行时动态加载器默认不搜索可执行文件旁边的 `lib/`；需要 RPATH：
  - Linux：`-Wl,-rpath,'$ORIGIN/../lib'`
  - macOS：`-Wl,-rpath,@loader_path/../lib`
- CMake 用 `BUILD_RPATH` / `INSTALL_RPATH` 设置，不要手工拼链接命令；见 [`LinkSettings.cmake`](../../configuring-cmake/assets/cmake/LinkSettings.cmake)。
- RPATH 里的 `$ORIGIN` 要防止被 shell 展开：CMake 字符串里写 `\$ORIGIN` 或使用 `BUILD_RPATH_USE_ORIGIN`。

## 验收：`file` 与 `ldd`

链接成功不等于能运行。构建后检查产物：

```bash
file build/clang/bin/app
ldd build/clang/bin/app
```

- `file` 确认架构、位数、是否动态链接。
- `ldd` 确认每个共享库都能解析到实际路径；出现 `not found` 就是加载期会失败。
- 运行 `app` 做一次最小启动；动态库缺失会在启动时暴露，而不是链接时。
- macOS 用 `otool -L` 代替 `ldd`；Windows 用 `dumpbin /dependents`。

## 构建脚本里的顺序

1. 配置：CMake 生成构建系统，导出编译数据库。
2. 编译 + 链接：构建所有 target。
3. 产物检查：确认 `bin/app`、`lib/`、编译数据库存在。
4. 运行：用项目入口命令启动，检查退出码和输出。
5. 测试：`ctest` 跑注册的测试。

不要用“链接成功”代替“运行成功”；也不要用“测试通过”代替“产物存在”。

## 检查清单

- [ ] 头文件自包含，普通函数定义不在头文件。
- [ ] 每个声明都有定义，且定义所在源文件加入 target。
- [ ] 静态库/共享库选择有理由，没有混用两套标准库。
- [ ] 产物在 `bin/` 与 `lib/`，RPATH 指向相对位置。
- [ ] `file` 与 `ldd` 检查过，程序能最小启动。
